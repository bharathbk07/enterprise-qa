# Full-stack architecture decisions

qa-architect coordinates requested full-stack assessments and owns the canonical quality plan. qa-orchestrate retains QA operations; qa-engineering retains performance/RCA/fix routing. Forward concrete tasks once and return results to the caller; do not bounce requests through repeated intake. For narrow requests load only the relevant role. An architecture assessment is not required before every selected test.

Assess available current implementation/runtime evidence first. Label code/configuration, documented intent, runtime observations and assumptions separately; a manifest does not prove deployed state. Prefer compatible improvements. Ask for project change strategy only when missing and consequential, then reuse it. Redesign needs an evidence-backed benefit/cost/risk case and a smaller alternative. Never invent budgets, targets, staffing or compliance obligations.

Select applicable functional correctness, performance, security, accessibility, data integrity, resilience/recoverability and maintainability/operability domains with reasons for exclusions/deferrals. Map stable requirements to sources, affected components, measurable acceptance or explicit unknowns, verification and outcomes. Untested/blocked is not passed. Delegate test design/execution to existing roles; native unit/component/contract/integration tests use the native-runner path without requiring a manual flow. Existing manual flow case counts and the flow-automation prerequisite remain intact.

Findings retain expected/actual behavior, safe reproduction or source location, environment/revision, evidence, impact and uncertainty. A reproduced bug does not automatically confirm its cause. Preserve mechanism proof plus logs/traces/metrics/code agreement for confirmed RCA; missing sources keep suspected/probable. Solution proposals name mechanisms, alternatives, compatibility, dependencies, cost assumptions, security/accessibility/reliability impacts, operability, rollout/rollback, owners and measurable validation. Distinguish proposed, accepted, implemented and validated; strategy acceptance does not approve application changes or deployment.

Static/read-only review is useful with partial access. Active security/load/fault/recovery/data/infrastructure actions require the concrete approved scope, limits and stop plan. Preserve the dedicated-browser, privacy, original-failure and fix-approval rules. Use selected product evidence roles and their permitted fallback; missing/truncated/pasted evidence constrains conclusions. No blanket enterprise-readiness or compliance certification.

Store only requested artifacts under qa/<application-id>/architecture/ and reference canonical knowledge, flows, cases, native runs and engineering evidence instead of duplicating history. Domain specialists return scoped contributions; qa-architect assembles quality-plan.json. Artifact writers/normalizers read the separately linked ARCHITECTURE-RECORDS.md when using the structured plan. scripts/architecture_checks.py checks local consistency only, not evidence truth, test execution or runtime authorization.
