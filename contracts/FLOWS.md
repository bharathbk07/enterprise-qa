# Business knowledge, manual flows and cases

Knowledge statements are observed, user-confirmed or assumed; preserve sources, dates, role and environment. A recording cannot establish expected behavior by itself. Preserve existing rules on conflict, attach new evidence and ask one question at a time with 3–4 choices and free text before replacing a rule. Incomplete flows remain incomplete. Version changed steps/rules; retain cases, runs and evidence. Mark impacted cases stale.

Manual cases: at least 20 distinct cases per flow, more as business rules require. Cover positive/negative, boundaries, validation, roles/permissions, recovery, API, basic accessibility, locale, browsers and responsive layouts where applicable. Do not pad with duplicate cases or invent business rules to reach 20: ask for missing rules and mark pending expected results. Use synthetic data if appropriate; preserve suitable existing data; clean up only data created by this run and track ownership.

Manual UI execution uses only a dedicated spawned QA browser through the qa-playwright specialist. Ask for human judgment only where necessary. Accept comma-separated flow names, numbers or IDs; resolve against the application index and ask on ambiguous/unknown items before any execution. Never treat a single flow selection as permission to execute every flow.

Flow naming and illustrated documentation: use the flow name explicitly supplied by the user. If none was supplied, suggest 2–3 concise business-oriented names from the stated goal or clarified recording and ask the user to select one or enter a custom name; when intent is unclear ask for the name directly. Ask one question at a time and allow free text. Never finalize an inferred name without confirmation. After browser closure combine proposed completion status, the suggested name, inferred steps and minor uncertainties into one guided review; confirmation resolves the displayed name/status together. Preserve stable flow ID/number and existing application identity; update the existing flow when selected rather than duplicating it. Naming-only changes preserve business flow version and existing execution eligibility; record prior names as aliases and ask about ambiguous name matches. Final manual flow documentation must embed the actual captured screenshot beside each corresponding numbered action, with observed outcome, expected outcome and evidence step ID. Copy approved evidence images to versioned flow-owned assets so deleting an original recording does not break the document. Respect the session's privacy choice and publication redaction rules. If a screenshot is missing, explicitly label the evidence gap and offer recapture in a dedicated spawned QA browser; never invent an image or substitute another step's screenshot. Partial flows remain clearly incomplete. Screenshot gaps and unresolved names must be visible in document readiness and handoffs.
