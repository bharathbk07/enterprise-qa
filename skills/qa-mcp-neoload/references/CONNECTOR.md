# NeoLoad execution and evidence

Sources checked 17 October 2026: [Web meta endpoint](https://docs.tricentis.com/neoload-web-v2/en-us/content/ai_integration/mcp_meta_tool.htm), [User Path MCP actions](https://docs.tricentis.com/neoload-latest/en-us/content/reference_guide/mcp_actions.htm), [Controller REST](https://docs.tricentis.com/neoload-latest/en-us/content/reference_guide/rest%20api.htm). Verify actual edition/release, region and supported Web versus Controller operations. No live test was launched.

NeoLoad Web's meta interface exposes discovery and execution wrappers; inspect the selected nested action's schema and effects before invocation. US/EU endpoints and API-token header must match the tenant. NeoLoad User Path MCP actions instead make the load runner an MCP client; installing them does not connect an assistant to Web results.

For results fallback use an already permitted official Web/Controller results API suitable for the deployment, or existing exports. The Controller REST server is separate from Web and may not be reachable; do not open ports or infer a cloud URL automatically. When direct reads are unavailable, ask the user to export the specific workspace/project/scenario/result ID and UTC window, with transaction counts/errors, percentile definition, throughput/unit, injector health and any aborted stages. Request aggregates rather than a complete raw request dump. Include pagination/filter limits and the scenario/build version in the handoff.

For launches, prepare the exact load model/stages, data/secrets, injector/license allocation, thresholds and stop plan. Execute once after approval. If a response is lost, reconcile the existing run before another launch; a timeout is not proof nothing started. Keep interrupted results and failed attempts. Browser scenarios must use dedicated runner-owned spawned browsers; protocol results do not require a browser. Do not treat Web result retrieval as execution or automatically retest from a pasted report.
